## 2. 역할과 규칙

### 역할 (사용자 지시)

"사용자가 목표와 채택 여부를 결정하고, Codex가 작업 지시와 검수를 맡고, Claude가 구현과 테스트를 담당한다."

### 지켜야 하는 규칙

| 규칙 | 내용 |
|---|---|
| 답하는 방식 | 한국어 합니다체. 결론 먼저. 쉬운 설명과 퍼센트 표. 추측은 추측이라고 표시. 실수는 바로 보고 |
| 브랜치 | `claude/great-planck-vnvyxx`에만 커밋·푸시. PR은 요청이 있을 때만. `main` 병합은 승인 후. 강제 푸시와 파괴적인 git 명령 금지 |
| 비밀 | 토큰·키를 묻지 않는다. 사용자 이메일을 외부로 보내지 않는다 |
| 계획 먼저 | 결과를 보기 전에 계획(`PREREG.md` 또는 `RULES.md`)을 커밋한다. 채택 조건도 미리 적는다 |
| 시험지 | 봉인 시험지는 한 번만 채점한다. **T3 ~ T9는 모두 쓴 시험지다. 후보 판정에 다시 쓰지 않는다.** 파일은 보관한다 |
| 사진 | 사진 파일은 커밋하지 않는다. 출처와 라이선스를 적은 목록만 바로 커밋한다 |
| 라이선스 | 표시 없는 사진도 학습에는 쓴다(사용자 결정). 저장소에는 올리지 않는다 |
| 출처 묶음 | 같은 사이트라도 다른 제보·게시물이면 다른 묶음으로 센다(사용자 결정) |
| 커밋 문구 | 모델 식별자를 넣지 않는다(정해진 귀속 줄 제외) |

### 협업 순서

1. 작업 전에 브랜치를 받아 빨리 감기(fast-forward) 한다.
2. 작업이 끝나면 `docs/codex_handoff.md` **맨 위**에 항목을 넣는다: 커밋, 바꾼 파일, 실제로 돌린 명령, 전후 결과, 통과한 테스트, 하고 싶은 것, 문제 있는 것.
3. 푸시한다.
4. GitHub Actions 결과를 확인해 노트에 적는다. (Claude가 확인하지 않아 CI가 깨진 채 넘어간 적이 있어서 생긴 규칙이다.)

## 3. 시스템 구조 (TV-13)

```
사진
 ├─ 채소 모델: EfficientNet-B0 (224픽셀, 10클래스 = 다섯 채소 × 정상/비정상)
 └─ CLIP ViT-B/16 (datacomp_xl_s13b_b90k) 이미지 특징
       ├─ 첫 번째 분류기 clip_head: 10클래스 + "다섯 채소 아님", 글 설명 점수 0.25 섞음
       └─ 두 번째 분류기 new_vegetable_head: 16클래스 + "여덟 채소 아님", 글 설명 점수 0.25 섞음

판정 (src/decision.py의 decide())
 1. 첫 단계: 채소 모델 + 첫 번째 분류기를 합쳐 다섯 채소 답 또는 "거름"
 2. 두 번째 분류기가 양파·고구마·대파일 확률을 0.8 이상으로 보면 그쪽 답으로 바꿈
 3. 감자 재확인(PC1): "상한 감자"라는 답만 CLIP 분류기에 다시 물어, 정상 쪽이 0.5 이상이면 "정상 감자"로 바꿈
 4. 확률이 0.9 미만이면 "판단 보류"로 보여 줌
 5. 상한 곳 지도: 채소 모델의 특징으로 그림(다섯 채소만)
```

| 파일 | 역할 |
|---|---|
| `src/predict.py` | 예측 명령과 `Classifier` 클래스 |
| `src/decision.py` | 판정 규칙 전체 |
| `src/train.py`, `train_clip_head.py`, `train_new_veg_head.py`, `calibrate.py` | 학습과 보정 |
| `app.py` | 웹 페이지(Gradio) |
| `tools/compare_on_dev.py` | 기준선과 후보를 같은 개발 사진에서 비교 |
| `tools/baseline_card.py` | 기준선 기록(`results/baseline/tv13.json`) |
| `tools/criteria/` (Codex) | 품질·누수·평가 방법 측정 스크립트 |

## 5. 대화의 흐름 (시간 순서)

### 5-1. 10월 ~ 11월 초: 모델 만들기 (압축된 구간)

### 5-2. 11월 19 ~ 22일: Codex와 협업 시작, 정리

- Codex가 데이터셋 도구 공통화 변경안과 독립 전체 리뷰를 냈다. Claude가 지적을 고쳤다(예측 출력, CLIP 캐시, 비교 도구).

- 기준선 기록과 비교 도구를 만들었다(`tools/baseline_card.py`, `tools/compare_on_dev.py`).
- 실수 정정: 감자·고구마 웹 개발 사진 162장 중 9장이 학습 행과 거의 같았다. 기록하고 결론은 유지했다.

### 5-3. 11월 22 ~ 23일: 새 시험지 T9 만들기

- Codex가 사진을 여섯 차례에 걸쳐 모았다(zip으로 전달). Claude가 확인하고 출처 묶음 단위로 나눴다.

- **T9**: 90장 = 상한 고구마 30, 상한 감자 30, 흙 묻은 정상 감자 30. 주 목록은 89장(1장이 T8 사진과 같은 그림). SHA-256으로 봉인했다.
- 채점기(`results/t9_test/score.py`)에 안전장치를 넣었다: 봉인 확인, 한 번만 실행, 임시 파일, Windows 경로 규칙.
- 상한 고구마 학습 사진 21장 추가 후보(SP1)는 개발 확인에서 탈락했다: 감자를 고구마로 답한 것이 2 → 5장, 다섯 채소 745 → 742장. T9를 열지 않았다.
- 사용자 사진 2차(41장): TV-12가 상한 고구마 0/15, 흙 묻은 감자 4/26.

### 5-8. 11월 25일: 사용자의 판단과 교수님 피드백

사용자의 판단:

- 대파가 구분이 안 되는 것 같다. 정확도가 낮으면 뺀다.
    - Claude가 다시 돌린 결과 모델에 막는 설정은 없었다. 개발 20장 중 14장이 대파(화면에 확정된 12장은 모두 맞음), 예전 시험지 44장 중 38장.

- "사진을 더 넣어도 개선이 안 되고, 넣으면 다른 것이 떨어진다 = 과대적합"이라는 판단에 대해 Claude는 **절반만 맞다**고 답했다. 벽에 부딪힌 것은 맞지만 이름은 과대적합이 아니라 **맞교환(trade-off)**과 **표현력의 한계**다.

- 중요한 사실: **EfficientNet-B0는 다섯 채소만 답한다. 고구마는 CLIP 분류기가 답한다.** 채소 모델을 키워도 고구마는 나아지지 않는다.

교수님 피드백(사용자가 전달): **"한 번에 밀지 말고 다단계로 해 봐라."**

1. 채소인지 과일인지 구분 → 채소면 2로
2. 정상인지 비정상인지 구분 → 비정상이면 3으로
3. 비정상이면 그 부분을 체크

Claude의 대조: 1단계(거르기)와 3단계(지도)는 이미 있고, 실제로 다른 것은 2단계(종류와 상태를 한 번에 답함)다. 지도는 다섯 채소만 된다.

- 남은 빈칸은 **고구마에는 2단계에 쓸 상한 흔적이 없다**는 것이다.
- 고구마는 2단계(판정)는 못 고쳤고, 3단계(상한 곳 표시)는 PatchCore 방식에서 처음 길이 보였다.

## 9. 알아 두면 좋은 것

- **클라우드 임시 폴더는 사라질 수 있다.** Claude가 받은 iNaturalist 사진 384장, 예전 실험 사진, 지도 그림이 거기에만 있다. 목록(`image_url`)으로 다시 받을 수 있고 모델 입력은 저장소에 있다.
- **개발 사진만으로는 채택하지 않는다.** 개발 사진은 TV-13을 고를 때 이미 쓴 사진이다. 새 봉인 시험지가 있어야 확정한다.
- **클래스당 사진이 적다.** 1 ~ 3장 차이는 우연과 구분되지 않는다. 숫자는 장수를 그대로 적는다.
- **지도가 "대체로 맞다"는 것은 눈으로 본 판단이다.** 정답 표시(마스크)가 없어 숫자로 재지 못했다.
- **상한 고구마의 틀리는 방식이 사진 묶음마다 다르다.** T9에서는 29장 중 12장이 "정상", 임시 폴더 사진에서는 51장 중 31장이 "다른 채소의 상함".
- 발표에서 쓸 수 있는 문장: "모델 성능이 정체 구간에 도달했고, 오류 분석과 절제 실험으로 병목이 정상/비정상 판정 단계와 고구마·감자의 종류 혼동에 있음을 확인했다. 현재 구조에서 시도한 개선책은 효과가 없어 알려진 한계로 보고한다."
