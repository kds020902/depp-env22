# 코딩·검수용 지시문 템플릿

코딩 에이전트(Claude, Codex)에게 일을 맡길 때 쓰는 지시문이다. `<...>`만 채워서 쓴다.
CLIP 판정에 들어가는 글 설명(영어 문장)과는 다른 것이다. 그쪽은 [`training_and_evaluation.md`](training_and_evaluation.md)의 "CLIP 글 설명" 절을 본다.

## 역할
| 누가 | 하는 일 |
|---|---|
| 사용자 | 목표를 정하고, 후보의 채택 여부를 결정한다 |
| Codex | 작업을 지시하고 결과를 검수한다 |
| Claude | 구현하고 테스트한다 |

## 공통 규칙 (세 템플릿 모두)
- **기준:** `claude/great-planck-vnvyxx`의 최신 커밋과 `docs/codex_handoff.md` 맨 위 항목
- **기준 모델:** TV-13(`model.pth`). 기록은 `results/baseline/tv13.json`에 있다. 사용자 결정 없이 `model.pth`를 바꾸지 않는다.
- **블라인드 시험지 T3~T9는 다 썼다.** 후보를 고르거나 개선을 주장하는 데 다시 쓰지 않는다.
- **끝나면:** 작업 브랜치에 올리고, `docs/codex_handoff.md` 맨 위에 아래 "결과 보고 형식"으로 적는다.
- 해 보지 않은 것은 "하지 않음"으로 적는다. 실패한 테스트는 출력과 함께 적는다.

### 결과 보고 형식
```
## <날짜> · <누가>: <한 줄 제목>
### 확인한 커밋 / 변경 파일
### 실제 실행한 명령
### 이전과 달라진 점        (같은 입력으로 전 → 후)
### 통과한 테스트           (개수와 명령)
### 하고 싶은 것
### 문제 있는 것 / 새 파일이 와야 확인할 것
```

## 1. 코드 정리

```
목표: <파일·폴더>의 <중복 / 쓰이지 않는 코드>를 정리한다. 줄 수를 줄이는 것보다 읽기 쉬운 구조와 기존 동작 보존이 먼저다.

입력 자료
- 대상: <경로>
- 근거: 실제 호출부와 실행 경로. 정리하기 전에 아래를 먼저 보고한다.
    - grep으로 찾은 호출부 (파일:줄)
    - README·테스트·워크플로·실험 스크립트에서 그 파일을 실행하는 명령
    - "쓰이지 않는다"는 판단은 호출부 0곳과 실행 명령 0곳을 함께 확인했을 때만 한다. 실험 기록에서 이름으로 가리키는 파일은 지우지 않는다.

변경 범위
- 고친다: <경로>
- 건드리지 않는다: model.pth, dataset/manifest.csv, results/**/scores*.json, 봉인된 t*_test.csv, 그 밖에 <경로>

유지할 동작
- 같은 입력에 같은 출력 파일(바이트 단위) / 같은 답과 확률 / 같은 명령줄 옵션과 종료 코드
- <이번 작업에서 특히 지킬 것>

검증 명령
- python -m pytest -q
- FULL_TESTS=1 python -m pytest -q                      (판정·예측 코드를 건드렸을 때. 시스템의 답은 CLIP이 있어야 확인된다)
- python tools/dataset_tools_equivalence.py OLD NEW     (dataset/tools를 건드렸을 때)
- python tools/rebuild_and_compare.py --work W ...      (데이터셋 만들기를 건드렸을 때, 약 17분)
- <옛 코드와 새 코드를 같은 입력으로 돌려 비교하는 명령>

통과 조건
- 위 명령이 모두 통과한다. 출력 비교는 "차이 0"이어야 한다.
- 동작이 달라지는 곳이 있으면 고치지 말고 먼저 보고한다.

결과 보고: 공통 형식 + 지운 것·합친 것마다 근거(호출부, 실행 경로) 한 줄
```

## 2. 버그 수정

```
목표: <증상>을 고친다.

입력 자료
- 재현 명령과 입력: <명령>, <가장 작은 입력>
- 지금 결과 / 기대 결과: <...> / <...>
- 의심 위치(있으면): <파일:줄>

변경 범위
- 원인이 있는 가장 작은 범위만 고친다. 주변 정리는 따로 제안한다.
- 건드리지 않는다: <경로>

유지할 동작
- 버그가 아닌 입력의 출력은 그대로다(테스트의 golden 답과 확률, 기존 파일 이름, 예전 캐시 읽기).

순서
1. 고치기 전에 실패하는 테스트를 먼저 쓰고, 실패하는 것을 확인한다.
2. 고친다.
3. 같은 테스트가 통과하는 것을 확인한다.

검증 명령
- python -m pytest -q <새 테스트>      (고치기 전 실패 → 고친 뒤 통과)
- python -m pytest -q
- FULL_TESTS=1 python -m pytest -q      (판정·예측 코드를 건드렸을 때)
- <재현 명령>                            (실제 명령으로 전 → 후)

통과 조건
- 재현 명령의 결과가 기대 결과와 같다.
- 기존 테스트가 모두 통과한다. 테스트의 기대값을 고쳐서 통과시키지 않는다(고쳐야 하면 이유를 보고한다).

결과 보고: 공통 형식 + 원인 한 문장 + "전 → 후" 표 + 아직 막지 못한 비슷한 경우
```

## 3. 모델 개선 실험

```
목표: <약점>을 <방법>으로 줄일 수 있는지 본다. 채택은 사용자가 결정한다.

입력 자료
- 기준 모델: TV-13 (results/baseline/tv13.json, results/baseline/tv13_dev.json)
- 개발 자료: tools/compare_on_dev.py의 세트 + <추가 자료>
- 새 학습 사진(있으면): <CSV. 출처·라이선스·주소 포함>

변경 범위 (변수 하나)
- 바꾸는 것: <하나만. 예: 상한 고구마 학습 사진 / 글 설명 문구 / 전환 기준>
- 고정: 나머지 가중치, 판정 기준, 시드, 개발 사진
- 결과물은 experiments/<이름>/ 에 둔다. 루트 model.pth는 바꾸지 않는다.

유지할 동작
- 기준 모델의 답은 그대로다(FULL_TESTS=1 python -m pytest -q의 golden 답과 확률).

순서
1. experiments/<이름>/PREREG.md를 결과보다 먼저 쓰고 커밋한다: 질문, 바꾸는 것, 개발 자료, 볼 숫자, 통과 조건, 예상.
2. 새 사진은 예전 사진·시험지와 CLIP 코사인 0.95 이상이면 뺀다. 사진 목록은 바로 커밋한다.
3. 후보를 만든다.
4. 기준 모델과 후보를 같은 개발 사진으로 비교한다.
5. 조건을 만족할 때만 새 블라인드 시험지를 만든다(RULES → 봉인 → 한 번 채점).

검증 명령
- python tools/compare_on_dev.py OUT.json <이름>=<후보.pth>     (채소 모델이 같을 때)
- python experiments/root_and_tomato/evaluate.py ...            (채소 모델을 다시 학습했을 때는 사진으로)
- python -m pytest -q

기록할 숫자 (기준 모델과 후보를 나란히, 몇 장 중 몇 장과 퍼센트)
- 클래스별 재현율
- 상함 → 정상 오류 (상한 사진을 같은 채소의 정상으로 답한 수)
- 판단 보류율 (확률 0.9 미만), 거른 비율
- 답을 낸 사진의 정확도
- 기준 모델과 답이 달라진 사진 수

통과 조건
- PREREG에 적은 조건을 그대로 쓴다. 결과를 보고 조건을 고치지 않는다.
- 조건을 고쳐야 하면 덧붙임으로 적고, 결과를 본 뒤에 고쳤다고 밝힌다.

결과 보고: 공통 형식 + 퍼센트 표 + "다음 단계로 가져감 / 반영 안 함" + 새 시험지에 필요한 사진 수
```
